# UBOS v5.10.8 — Production-Safe High Availability, Control Failover, and Automation State Recovery

## Status

Planned

---

# Vision

Enable UBOS to continue operating safely when a control node, service, process, workstation, network path, or automation component fails.

The platform must detect failures, preserve authoritative production state, transfer control to a healthy standby, restore incomplete automation, and prevent conflicting commands or duplicate execution.

UBOS must answer:

```text
Which node currently owns production control?

Is that node healthy?

Can another node safely assume control?

What commands already executed?

Which workflows remain incomplete?

What state must be restored?

How do we prevent two nodes from controlling Program at once?
```

This phase establishes the operational-resilience foundation required for professional broadcast, enterprise production, continuous channels, and remote live operations.

---

# Strategic Purpose

Previous phases introduced:

```text
Timed Scheduling

↓

Workflow Automation

↓

Production Rules

↓

Authorization and Approval

↓

Audit and Incident Reconstruction
```

UBOS v5.10.8 ensures those capabilities remain trustworthy during infrastructure failure.

Without controlled failover, advanced automation could:

* stop unexpectedly
* execute twice
* lose schedule position
* repeat a scene transition
* restart an already-running stream
* activate competing outputs
* split production authority between nodes
* recover into an incorrect state

The high-availability layer must prevent these conditions.

---

# Lease Renewal

The leader must renew its lease before expiration.

```text
Leader Healthy

↓

Renew Lease

↓

Continue Production Authority
```

If lease renewal fails:

```text
Stop Accepting New Production Commands

↓

Enter Isolation Protection

↓

Allow Standby Election
```

The old leader must not continue controlling production after losing its lease.

---

# Fencing Tokens

Every leadership term receives a monotonically increasing fencing token.

Example:

```text
Leader A

Token 41
```

After failover:

```text
Leader B

Token 42
```

All downstream command targets must reject commands carrying stale tokens.

This prevents the old leader from issuing valid commands after network isolation.

# Leader Election

Leader election must be deterministic and quorum-aware.

Possible implementation approaches include:

* Raft-based consensus
* an external consensus store
* database-backed lease with fencing
* distributed lock service with quorum guarantees

The implementation must not use a simple shared boolean such as:

```text
isPrimary = true
```

---

# Leader Election Requirements

Election must consider:

* voting membership
* current term
* node health
* replication freshness
* software compatibility
* schema compatibility
* production eligibility
* quorum availability
* operator maintenance locks

---

# Leadership Eligibility

A node must not become leader if:

* its replicated state is stale beyond policy
* its software version is incompatible
* its schema migration is incomplete
* its audit journal is unhealthy
* its clock is unsynchronized beyond tolerance
* required production services are unavailable
* it is under maintenance
* it is quarantined
* it lacks valid authorization credentials

---

# Quorum

For a three-voter cluster:

```text
2 of 3 votes required
```

A node must not self-elect without quorum unless an explicit disaster-recovery policy permits controlled single-node operation.

---

# Witness Node

A witness may participate in election without running full production services.

Purpose:

```text
Prevent Split Brain

Provide Third Vote

Confirm Cluster Membership
```

The witness must not become production leader unless explicitly designed to do so.

---

# Split-Brain Prevention

Split brain occurs when more than one node believes it controls production.

UBOS must prevent this through:

* quorum
* expiring leases
* fencing tokens
* downstream token enforcement
* membership consensus
* command idempotency
* automatic isolation of stale leaders

# Replication Modes

Support configurable durability modes.

## Synchronous

```text

↓

↓

Command confirmed
```

Best for critical state, with higher latency.

## Near-Synchronous

```text

↓

↓

```

Useful where low latency is essential.

## Asynchronous

Suitable only for noncritical data such as analytics or historical reports.

# Idempotent Command Execution

Every recoverable command requires an idempotency key.

Example:

```text
start-recording:production-892:segment-001
```

If the same command is retried after failover, the target returns the original result rather than performing it again.

* lease expires
* critical service fails

# Automatic Failover Safety Gate

Before assuming control, the standby must verify:

* valid quorum
* highest known term
* current fencing token
* replication freshness
* durable audit path
* compatible configuration
* production output reachability
* authorization availability
* no active maintenance block

# Manual Failover

Operators should be able to initiate:

```text

```

```text

↓

↓

↓

↓

↓

```

# Forced Failover

Forced failover is allowed only for authorized supervisors when the normal leader cannot release control.

Requirements:

* quorum confirmation
* fencing-token advancement
* stale-leader isolation
* explicit reason
* critical alert
* full audit record
* post-failover review

Returning control to the original node must be controlled.

The recovered node first becomes:

```text

↓

↓

```

It must not immediately reclaim leadership.

# Media-Plane Separation

The control plane must be separated from the media plane.

A control-node failover should not automatically stop:

* active encoders
* media pipelines
* recording processes
* network streams
* device playback
* audio routing

Whenever possible, media services should continue their last valid state independently.

---

# Hold-Last-State Behavior

During temporary control loss:

```text
Program output remains unchanged

Streaming continues

Recording continues

Audio routing remains stable

Graphics remain in their last valid state
```

No uncontrolled fallback should occur unless explicitly configured.

---

# Autonomous Media Services

Media services should expose:

* current state
* command history
* fencing-token validation
* idempotency support
* health state
* local safety behavior
* reconnect capability

This allows the new leader to reconcile without restarting the media pipeline.

---

# Device Failover

Some production devices may support dual control paths.

Examples:

* primary and backup switcher connection
* redundant encoder API endpoints
* dual recorder control
* redundant graphics engine
* mirrored replay engines

UBOS should model control-path availability separately from device health.

---

# Output Failover Coordination

Control failover is not the same as output failover.

UBOS must distinguish:

```text
Control Node Failed

Media Output Still Healthy
```

from:

```text
Media Output Failed

Control Node Healthy
```

Different recovery workflows apply.

# Quorum Loss

If the leader loses quorum:

```text
Stop issuing new cluster-controlled commands

↓

Preserve media state

↓

Attempt lease-safe isolation

↓

Notify operators

↓

Allow predefined emergency local controls
```

# Emergency Local Control

A deployment may define a local emergency control panel that remains available during cluster failure.

Allowed actions may include:

* take emergency slate
* mute dangerous audio source
* stop compromised output
* preserve recording

# Acceptance Criteria

UBOS v5.10.8 is complete when:

* UBOS can operate with an active control node and one or more synchronized standby nodes.
* Only the valid leader can issue production-changing commands.
* Leadership uses quorum, leases, terms, and fencing tokens.
* Downstream production services reject stale-leader commands.
* Production state, command journals, automation state, approvals, locks, and audit continuity replicate to standby nodes.
* A healthy standby can assume control after leader failure without restarting healthy media outputs.
* Already-completed commands are not executed twice after failover.
* Uncertain commands are reconciled against actual target state before retry.
* Scheduler timelines, timers, recurring events, and missed-event policies recover deterministically.
* Running workflows resume, retry, reconcile, roll back, or pause according to declared recovery policies.
* Rule cooldowns, counters, debounce, suppression, and pending decisions recover correctly.
* Pending approvals and authorization controls remain valid and context-safe after failover.
* Split-brain scenarios are prevented through quorum and fencing.
* Quorum loss causes safe degraded behavior rather than unrestricted control.
* Operators can perform controlled failover, forced failover, and planned leadership transfer with proper authorization.
* Recovered nodes synchronize fully before becoming leadership-eligible.
* Failback does not occur unexpectedly during a live production.
* Rolling upgrades can be performed through controlled leadership transfer.
* Every failover, reconciliation decision, and recovery outcome is fully audited.
* HA status, replication lag, quorum, leadership, and recovery progress are visible to operators.
* Chaos and long-running tests demonstrate bounded recovery without command duplication or media disruption.
