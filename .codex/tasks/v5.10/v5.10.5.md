# UBOS v5.10.5 — Production-Safe Rules Engine, Conditional Automation, and Policy-Based Production Control

## Status

Planned

---

# Vision

Extend UBOS automation beyond fixed macros and predefined workflows by introducing a deterministic **production rules engine**.

UBOS should be able to continuously evaluate production state and decide:

```text
When this happens

and these conditions are true

perform these actions

unless an operator or safety policy blocks them
```

This enables intelligent automation without giving uncontrolled authority to scripts, plugins, or future AI systems.

The rules engine becomes the decision layer between:

```text
Production State

↓

Events and Signals

↓

Policies and Conditions

↓

Approved Production Actions
```

---

# Strategic Purpose

The scheduler determines **when** something should happen.

The workflow engine determines **how** a sequence should execute.

The rules engine determines:

```text
Whether an action should happen

Which action should happen

Under what conditions

With what restrictions

At what priority
```

Together, these systems form the UBOS production automation foundation.

# Rule Structure

Every production rule follows:

```text
WHEN

an event occurs

IF

one or more conditions are satisfied

THEN

perform one or more actions

ELSE

perform an optional fallback

UNLESS

a blocking condition or safety policy applies
```

Example:

```text
WHEN

Guest microphone becomes active

IF

Guest camera is available

AND

Guest lower-third data exists

THEN

Preview Guest Camera

Show Guest Lower Third

ELSE

Notify Operator
```

# Hysteresis


# Recursion Protection

A rule action may change state and trigger another rule.

The engine must track:

```text
Decision cycle ID

Trigger chain ID

Parent rule ID

Execution depth

Previously executed rules
```

Example loop to prevent:

```text
Rule A sets Variable B

↓

Rule B sets Variable A

↓

Rule A triggers again
```

The engine must detect and block cyclic rule execution.

# Rule Evaluation Cycle

```text
Production Event Received

↓

Normalize Event

↓

Capture Immutable State Snapshot

↓

Find Relevant Rules

↓

Evaluate Conditions

↓

Apply Policy Restrictions

↓

Resolve Conflicts

↓

Validate Actions

↓

Submit Approved Commands

↓

Record Decision
```

Rules in the same cycle must evaluate against the same state snapshot.

This prevents earlier rules from unpredictably altering the evaluation of later rules.

# Deterministic Evaluation

The engine must guarantee that identical:

```text
Rules

State

Events

Configuration
```

produce identical decisions.

Avoid:

* random action selection
* unordered iteration
* direct wall-clock access
* mutable shared state
* uncontrolled plugin callbacks
* nondeterministic network responses during evaluation

External data must be normalized before entering the evaluation context.

---

# Rule Validation

Before activation, validate:

* unique rule identifier
* valid trigger
* valid fields
* valid operators
* type compatibility
* valid action commands
* valid targets
* valid permissions
* valid policy reference
* no obvious recursion cycle
* no illegal emergency action
* no impossible condition
* no conflicting exclusive actions inside one rule

Invalid rules must remain disabled.

# Automation Modes

Support clear production modes:

```text
Off

Observe

Recommend

Confirm

Automatic
```

## Off

Rules are not evaluated.

## Observe

Rules evaluate and log decisions but take no action.

## Recommend

Rules present suggested actions to the operator.

## Confirm

Rules require approval before execution.

## Automatic

Approved rules execute automatically within their permissions.

This allows gradual and safe adoption.

# Performance Goals

Target:

* 100,000+ registered rules
* indexed trigger lookup
* no full rule-set scan for common events
* less than 2 ms evaluation for common rule groups
* bounded action execution queues
* deterministic conflict resolution
* zero uncontrolled recursive execution
* safe recovery after restart

Frame-critical switching must still pass through the existing real-time command path.

The rules engine should decide what to do without blocking rendering or media-processing threads.

---

# Recovery Requirements

After restart, UBOS must restore:

* active policies
* enabled rules
* cooldown state where necessary
* pending confirmations
* incomplete decision records
* execution counters
* suppression state

Actions must not execute twice after recovery.

Use idempotency keys for all rule-generated commands.

---

# Security Requirements

Rules must not:

* execute arbitrary operating-system commands
* bypass the Command Bus
* directly mutate production state
* access secrets without permission
* activate emergency actions without authorization
* accept unauthenticated external triggers
* display unmoderated social content automatically
* silently change their own permissions

All external inputs must be authenticated, normalized, and validated.

---

# Acceptance Criteria

UBOS v5.10.5 is complete when:

* Operators can create rules using event, state, timing, and variable conditions.
* Rules support nested `AND`, `OR`, and `NOT` logic.
* Rules can execute individual actions or start complete workflows.
* Policies can group, authorize, prioritize, suppress, and govern rules.
* Conflicting rule actions are resolved deterministically.
* Cooldowns, debounce, hysteresis, recursion protection, and execution limits work reliably.
* Operators can run rules in observe, recommend, confirm, or automatic mode.
* Every rule decision is explainable and fully auditable.
* Rules can be tested through dry runs, simulations, and historical event replay.
* Rules cannot bypass production permissions or safety controls.
* Engine recovery does not duplicate previously executed actions.
* The rules engine performs safely under realistic production load.
* All automation remains interruptible by authorized operators.
