# UBOS v5.10.6 — Production-Safe Operator Roles, Automation Permissions, and Approval Control

## Status

Planned

---

# Vision

Introduce a production-grade authorization and approval system that ensures every operator, automation rule, workflow, API client, plugin, and future AI agent can perform only the actions explicitly permitted within its assigned production scope.

UBOS must answer four questions before every sensitive action:

```text
Who is requesting the action?

What are they allowed to do?

Where are they allowed to do it?

Does this action require approval?
```

This phase establishes the trust boundary for all manual and automated production control.

---

# Strategic Purpose

The scheduler decides **when** an action runs.

The workflow engine decides **how** multiple actions run.

The rules engine decides **whether** an action should run.

The authorization system decides:

```text
Who may request it

Who may approve it

Which resources may be affected

Which safety restrictions apply
```

Without this layer, advanced automation cannot be considered production-safe.

---

# Core Objectives

UBOS v5.10.6 must provide:

* operator identities
* service identities
* role-based access control
* attribute-based restrictions
* resource-scoped permissions
* action-level authorization
* multi-stage approval
* production locks
* temporary privilege elevation
* automation authority boundaries
* emergency override governance
* complete security auditing

# Deny by Default

UBOS must follow:

```text
No explicit permission

↓

No authorization
```

Permissions must be granted intentionally.

Implicit access through UI visibility is not sufficient.

---

# Command Bus Enforcement

Every production command must pass through authorization before execution.

```text
Command Requested

↓

Identity Resolved

↓

Permission Evaluated

↓

Scope Evaluated

↓

Locks Evaluated

↓

Approval Evaluated

↓

Command Validated

↓

Command Executed
```

No subsystem should bypass this path for operator-facing or automation-generated actions.

---

# Automation Authority

Each workflow, rule, macro, and scheduled event must execute under its own service identity.

Example:

```text
Workflow:

Commercial Break

Authority:

May switch approved scenes

May start approved playback

May mute assigned music bus

May not stop master stream
```

The workflow must not automatically inherit the permissions of its creator at runtime.

---

# Delegated Authority

An operator may start a workflow using delegated authority.

```text
Operator starts workflow

↓

Workflow assumes its own fixed permissions

↓

Workflow cannot exceed approved authority
```

This prevents a highly privileged creator from unintentionally producing permanently overpowered automation.

---

# Permission Intersection

For some executions, effective permissions should be:

```text
Operator Permissions

INTERSECT

Workflow Permissions

INTERSECT

Current Production Policy
```

This prevents either side from expanding the other.

---

# Static Automation Authorization

Before activation, UBOS should inspect workflow and rule actions.

Example:

```text
Workflow contains:

Start Stream

Delete Recording
```

If its identity lacks `recording.delete`, activation must fail.

---

# Runtime Authorization

Static validation is not enough.

Every action must also be authorized at runtime because:

* roles may change
* policies may change
* production state may change
* locks may be active
* credentials may expire
* scopes may change

---

# Approval Control

Examples:

* start public stream

* delete recording
* activate emergency broadcast
* publish unverified social content
* change automation policy
* update operator roles
* replace active rundown
* take a remote guest directly to Program

It should not automatically allow:

```text

Change roles

Export secrets

Disable audit logging
```

# Degraded-Mode Behavior

If authorization services become unavailable:

```text
Read-only operations may continue

Previously approved low-risk controls may continue where policy permits

New high-risk actions must fail closed

Emergency local controls may use a predefined break-glass policy
```

UBOS must never silently switch to unrestricted mode.

# Acceptance Criteria

UBOS v5.10.6 is complete when:

* Every operator and automated component has an explicit identity.
* Roles and permissions can be assigned with resource and environment scopes.
* Every sensitive production command is authorized before execution.
* Workflows, rules, schedulers, plugins, devices, APIs, and AI services operate under restricted service identities.
* High-risk actions can require single, dual, or quorum approval.
* Approval requests are context-bound, expiring, auditable, and protected against replay.
* Production locks can restrict automation, configuration, and Program control.
* Temporary privilege elevation and emergency break-glass access are limited and audited.

* Operators can understand why an action was allowed, denied, or held for approval.
* Security policies can be simulated and impact-tested before activation.
* Authorization state recovers safely without duplicating approved actions.
* The system fails closed for high-risk actions during authorization failure.
* No production subsystem can bypass the authorization boundary.
